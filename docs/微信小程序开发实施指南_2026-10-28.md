## 0. 先给结论：能做，但顺序不能错

### 0.1 三个可行性问题

| 问题 | 结论 | 依据 |
|---|---|---|
| 小程序能不能做 BLE 配网？ | ✅ **能** | 微信提供完整 BLE 中央设备 API，覆盖搜索/连接/读写/通知 |
| 协议帧能不能过？ | ✅ **能，而且是卡片级的刚好** | 帧 = PAYLOAD 14 + 帧头尾 5 = **19 字节**，小程序单次写上限 **20 字节** |
| 加密要不要自己实现？ | ⚠️ **要，这是最大工作量** | AES-128-ECB/PKCS7 + RSA-1024 密钥协商，小程序无内置 crypto |

> 那个 19 vs 20 不是巧合：协议当初就是按 BLE 默认 MTU 23（有效载荷 20）设计的。
> 但**余量只有 1 字节**，固件侧任何一帧超长都会在小程序上直接丢。这是必须盯住的约束。

### 0.2 小程序做不了的事（先划清边界，免得中途返工）

| 限制 | 影响 |
|---|---|
| 🔴 **iOS 小程序禁虚拟支付** | 点卡、订阅**首版不能卖**。要么首版免费，要么只上 Android |
| 开发者工具**不支持 BLE** | 全程真机调试，模拟器只能看页面 |
| 不能设 MTU | 只能吃默认 20 字节，协议不能改 |
| 不能直接写 CCCD | 靠 `notifyBLECharacteristicValueChange` 内部代写，特征若只声明 INDICATION 会失败 |
| 后台不能持续 BLE | 配网必须在前台完成，切后台会断 |
| request 域名需备案 + HTTPS | `nglearn.turingapi.com` 要确认已备案，且每月只能改 5 次 |

### 0.3 🔴 第一天必须验证的三件事（不要跳过）

这三件事决定整个方案成不成立。没验证就开写页面，等于赌。

| # | 验证什么 | 怎么验 | 不通怎么办 |
|---|---|---|---|
| **V1** | 小程序能不能收到设备的 BLE 帧 | 连上设备 → 开通知 → 发一帧 `0x0D` 空参请求 → 看有没有 `0x8D` 回来 | 检查特征 UUID、通知是否真开、CRC 是否算错 |
| **V2** | **不做加密（明文）设备认不认** | 直接发明文帧（flag 不带 `0x80`）。App 里就有明文降级路径，说明协议允许 | 若不认，必须实现 RSA + AES，工期 +3~5 天 |
| **V3** | iOS 能不能扫到、广播包解析对不对 | iPhone 真机扫设备，看能不能拿到 `AIPicCameraXXXX` | iOS 广播包可能被截断，需改按名字匹配 |

**V2 是整个排期的分水岭。** 建议第一天只做 V1+V2，通了再谈页面。

### 2.3 多语言

App 有 4 档界面语言（zh / zh-Hant / en / ar），小程序照搬，但**别用 i18n 框架**，一个扁平字典就够：

```js
// i18n/index.js
const dict = {
  zh:  { tab_record: '记录', ... },
  'zh-TW': { tab_record: '記錄', ... },
  en:  { tab_record: 'Records', ... },
  ar:  { tab_record: 'السجلات', ... },
```

**阿语是 RTL**：`app.json` 里加 `"resizable": true`，并在 `app.wxss` 用 `direction: rtl`（阿语时动态挂 class）。

## 3. 阶段二：接云端（2 天）

### 3.1 接口清单（与 App 完全一致，无需新接口）

| 用途 | 接口 |
|---|---|
| 记录列表 | `GET /api/record/list?key={apikey}&deviceId={id}&page=&size=&lang=` |
| 卡片详情 | `GET /api/record/detail?id=` |

### 3.2 封装

```js
// utils/api.js
const BASE = 'https://nglearn.turingapi.com'

function request(path, data) {
  return new Promise((resolve, reject) => {
    wx.request({
      url: BASE + path,
      data,
      method: 'GET',
      timeout: 10000,
      success: (res) => {
        const b = res.data || {}
        if (b.code === 0) resolve(b.data)
        else reject(new Error(b.msg || ('code=' + b.code)))
      },
      fail: (e) => reject(new Error(e.errMsg)),
    })
  })
}
```

> 🔴 `size` 上限 **100**，翻页别超过。
> 🔴 错误码 `4005` = apikey 无效、`4006` = deviceId 无效、`40000` = 记录不存在，要分别给文案。
> 🔴 **不要给这些请求加加密或签名。** AES + `secret` 那套只属于**设备 → 云端**（固件里已实现）；`secret` 不可能进小程序包，加了就是把密钥公开。App / 小程序侧就是明文 HTTPS，带 `key` + `deviceId` 即可——与 `nglearn` 读接口现状一致（curl 明文直通）。
> 🔴 反过来说，`apikey` 明文放在包里等于公开，这是**现状既有问题**，本版接受；收口方案见《上线计划》的两级凭证（`device_secret` → `access_token`），不在本版范围。

## 4. 阶段三：BLE 配网（5~8 天，难点全在这）

### 4.1 完整时序（与 App 一致）

```
搜设备 → 连接 → 取服务/特征 → 开通知
  → ① 密钥协商（0x0F / 0x8F，RSA-1024）      ← 明文可跳过
  → ② 查设备信息（0x0D / 0x8D）              ← 拿 apikey + deviceId
  → ③ 扫热点（0x0E → 0x8E 多条 0x88 + 0x89）
  → ④ 配网（0x0A / 0x8A，SSID + 密码）
  → ⑤ 绑定回传（0x11 / 0x91）
  → ⑥ 设备配置（0x12，设备可忽略，不等回执）
```

### 4.2 关键参数（照抄，别自己猜）

| 项 | 值 |
|---|---|
| Service UUID | `00001824-0000-1000-8000-00805F9B34FB` |
| 写 / 通知特征 | `00002ABC-...`（**同一个**，官方 SDK 设计如此） |
| 单帧上限 | 19 字节（PAYLOAD 14） |
| AES | **ECB**/PKCS7，128 位（不是 CBC，文档写错过） |
| CRC8 | 联盛德私有表，**不能换成标准实现** |

**Frame Flag 三个位（语义有反直觉的地方，务必看清）**

| 位 | 值 | 含义 |
|---|---|---|
| ENCRYPT | `0x80` | 本帧 PAYLOAD 已加密 |
| ACK_REQ | `0x40` | **要求对方回 `0x10`**。设备发来的帧带此位时，必须立即回 |
| LAST_PACKET | `0x20` | 🔴 **置位 = 后面还有帧**；**未置位 = 这是最后一片** |

> `LAST_PACKET` 是反的：名字像「最后一片」但置位表示「还有」。判断收齐只能看这一位，
> **不能靠 `no` 序号**——设备不会告诉你总片数。

**TLV 格式（长度字段只有 1 字节，最容易写错）**

```
Type(1) + Length(1) + Value(N)
```

写成长度 2 字节小端，设备会整帧解析失败。`packet.js` 已按此实现并逐字节对照验证过。

### 4.3 四步推进，每步都有验收

#### 第 1 步：扫到 + 连上（0.5 天）

```js
const ble = new BleClient()
await ble.openAdapter()
await ble.startScan((list) => { console.log(list) })
// 用户点选后
await ble.connect(item.deviceId)
```

验收：控制台能打出 `AIPicCameraXXXX`，连接成功且不报 4402/4403。

#### 第 2 步：发一帧、收一帧（1 天）—— 🔴 全项目最关键的一步

先验证**明文**能否通：

```js
const ble = new BleClient()
// 收帧回调：设备发来的完整消息会在这里回调
ble.on('message', (cmd, payload, encrypted) => {
  console.log('收到 cmd=0x' + cmd.toString(16), BleClient.toHex?.(payload) || payload)
  const tlvs = decodeTlv(payload)          // 注意：must 用数组，不能转 Map
  console.log('TLV 条数=', tlvs.length)
})
ble.on('log', console.log)

// 发 0x0D 空参查询；无参请求必须有零长占位 TLV
const tb = new TlvBuilder().putPlaceholder()
await ble.send(CMD.QUERY_CONFIG, tb.build(), { encrypt: false })
// ack 默认 false —— 发送方向不要求回执；设备若要 Ack，ble.js 会自动回 0x10
```

验收：`message` 回调被触发，`cmd` 为 `0x8d`，`decodeTlv()` 拆得出 TLV。

> **如果不通**，按这个顺序查：
> 1. CRC 算错（最常见）→ 拿 App 发出的帧做对照，逐字节比
> 2. 通知没开成功 → 看 `properties` 里有没有 `notify`/`indicate`
> 3. 帧超 20 字节 → 打日志看长度
> 4. 设备强制加密 → 走第 4 步

#### 第 3 步：扫热点 + 配网（2 天）

```js
// 扫
await ble.send(CMD.WIFI_SCAN, new TlvBuilder().putPlaceholder().build(), { encrypt: false })
// 设备回多条 0x8E，每帧 TLV 0x88 是一行：序号|RSSI|AUTH|SSID
// 🔴 必须用数组收，不能用 Map —— 同帧会有多条 0x88
const list = decodeTlv(payload).filter(t => t.type === 0x88).map(t => parseApLine(t.value))
```

`parseApLine` 的坑：**SSID 是第 3 个竖线之后的内容**，不是第 2 个（旧文档写错过）。

```js
// 配网
const tb = new TlvBuilder()
  .putString(TLV.AP_SSID, ssid)
  .putString(TLV.AP_PASSWORD, pwd)
await ble.send(CMD.CONFIG_STA, tb.build(), { encrypt: false })
```

验收：`0x8A` 回 `0x00`。

#### 第 4 步：补加密（3 天，可延后）

只有 V2 验证不通过才必须做。分两块：

| 块 | 做什么 | 难度 |
|---|---|---|
| AES | `aes-128-ecb` + PKCS7。小程序用 `crypto-js`（npm 构建）或自写 | 中，半天能通 |
| RSA-1024 | 生成密钥对 → 发公钥 → 解设备返回的密文 → 得到 AES 会话密钥 | **高**，3 天量级 |

RSA 这块的现实做法：
- npm 装 `node-rsa`（纯 JS），或用 `jsencrypt`
- **密钥生成很慢**，小程序 JS 环境生成 RSA-1024 可能 1~3 秒 → 必须给 loading，别让用户以为卡死
- 随机源用 `wx.getRandomValues()`，不要用 `Math.random()`

> 我的建议：**先按明文交付第一版**，加密作为第二阶段。
> 理由：配网是一次性动作，明文只暴露在用户自己家的 30 秒内；而 RSA 会让首版工期翻倍。
> 但这条要和产品/安全确认，因为传的是 WiFi 密码。

## 6. 坑清单（12 条，都是真踩过的）

| # | 坑 | 后果 | 对策 |
|---|---|---|---|
| 1 | 帧超过 20 字节 | 小程序静默写失败 | 固件侧锁死 14 字节 PAYLOAD |
| 2 | 用 `Map` 收 TLV | 多条 `0x88` 只剩最后一条，热点少报 | 用数组 `decodeTlv()` |
| 3 | 按 SSID 去重 | 同名不同 BSSID 被吞 | 按 `0x88` **序号**去重 |
| 4 | SSID 解析取第 2 个竖线 | 名称被截断 | 取**第 3 个**竖线之后 |
| 5 | 连发不等回调 | ATT 队列堵死，只发出去一两片 | 发一片等一片，间隔 30ms |
| 6 | 不 `closeBLEConnection` 就重连 | 链路泄漏，第 6~7 次必断 | 每次重连前先 close |
| 7 | CCCD 写成 INDICATION | 只支持 NOTIFY 的特征回 133 | 靠 `notifyBLECharacteristicValueChange`，不要手写 |
| 8 | 无参请求不发占位 TLV | 设备不响应 | `putPlaceholder()`（2 字节 `00 00`） |
| 9 | CRC 用标准实现 | 设备拒收所有帧 | 用 `crc8.js` 里的私有表 |
| 10 | AES 用 CBC | 全部通信失败 | **ECB**（三端官方 Demo 都是 ECB） |
| 11 | 用 `Math.random()` 做密钥 | 密钥可预测 | `wx.getRandomValues()` |
| 12 | 把 5G 热点也上报 | 用户选了连不上 | 只报 2.4G |
| 13 | 🔴 **TLV 长度写成 2 字节** | 设备整帧解析失败，所有帧无响应 | 长度只有 **1 字节** |
| 14 | 🔴 **靠 `no` 序号判断收齐** | 多分片响应永远拼不齐 | 看 `flag & 0x20`（置位=还有） |
| 15 | 🔴 **不回 `0x10` Ack** | 多分片响应卡住，重发几次才勉强成功 | 收到 `flag&0x40` 就回，Payload 是 1 字节裸 seq |
| 16 | 🔴 **不校验 `seq` 连续性** | 重发帧被当新帧，数据错乱 | 逐片比对，不连续就丢弃 |
| 17 | 把 `0x10` Ack 当数据解析 | 解码出乱码 | `cmd === 0x90` 直接 return |
| 18 | 收帧回调里同步 `await` 写 | 阻塞后续通知 | Ack 用 fire-and-forget |
| 19 | 🔴 **分片序号 `no` 从 1 开始** | 设备按 0 基解析，可能丢首片 | `no` **0 基**，第一片是 0 |
| 20 | 发送时带了 ACK_REQ 位 | 设备回 `0x10`，与预期不符 | 发送方向 `ack` 恒 false（App 即如此） |
| 21 | 🔴 **非末片不置「还有后续」位** | 设备把第一片当完整帧，后半截丢失 | 非末片置 `0x20`，`send()` 已处理 |
