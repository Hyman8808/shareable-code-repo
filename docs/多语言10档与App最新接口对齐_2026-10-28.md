## 1 界面语言：10 档怎么落的

### 1.1 为什么是 10 而不是 9

产品口径的「9 种语言」指**物品名称语言**（`zh` / `zh-Hant` / `ja` / `ko` / `es` / `fr` / `de` / `ru` / `ar`，另有 `none` 仅英文开关）。
界面语言除了这 9 种，还必须保留**英文界面**（`en` 是历史就有的第 4 档，且是外语用户的兜底），因此界面一共 **10 档**。

### 1.2 App 侧

| 文件 | 改动 |
|---|---|
| `data/i18n/UiLanguage.kt` | 新增 6 个常量（`JA/KO/ES/FR/DE/RU`）；`ALL` 列表统一 10 档（tag + 本地写法 + 副标题资源）；`normalize()` 补 6 个分支并支持 `zh-Hant`；`displayNameOf()` 改为查 `ALL` |
| `res/layout/dialog_ui_language.xml` | 由「4 行写死」改为 `ScrollView + container`（10 × 62dp 超小屏装不下） |
| `res/layout/item_ui_language.xml` | 新增：一行 = 语言名 + 副标题 + 勾选 |
| `ui/profile/ProfileFragment.kt` | `pickUiLanguage()` 按 `UiLanguage.ALL` 动态 inflate，最后一行隐藏分隔线 |
| `res/values-{ja,ko,es,fr,de,ru}/strings.xml` | 新增 6 份，各 451 条 |

🔴 **语言名不翻译**：`ALL` 里的 `name` 是「中文（简体）/ 日本語 / Русский / العربية」这种本地写法，硬编码在 Kotlin 里而不是走 strings —— 切到阿语界面后，「日本語」若被翻成阿语，日语用户就找不到自己那项了。副标题才跟随界面语言。

🔴 **`normalize()` 的 `else -> ZH` 是静默陷阱**：新增语言漏加分支时不会报错，表现为「设置里选了俄语、界面还是中文」。本次 6 种语言逐个加分支，并补了 `zh-Hant → zh-TW`。

### 1.3 小程序侧

| 文件 | 改动 |
|---|---|
| `utils/prefs.js` | `UI_LANGS` 10 档，`sub` 改为 `subKey` 走 i18n（原来写死中文）；`normalizeUi()` 补 6 分支 + `zh-Hant` |
| `utils/i18n.js` | `PACKS` 注册 10 份语言包 |
| `pages/language/language.js` | `uiList` 副标题改为 `i18n.t(l.subKey)`，跟随当前界面语言 |
| `utils/lang/{ja,ko,es,fr,de,ru}.js` | 新增 6 份，各 531 键 |

切换界面语言仍走 `wx.reLaunch` 重载（App 是重建 Activity），否则已渲染页面会半新半旧。

## 2 文案从哪来：一份译表，两端生成

```
tools/i18n_src/
  zh.tsv        简体基准：决定键顺序 + 缺失回退
  en.tsv        英文对照（不参与生成）
  p1..p4.tsv    6 语译表，列序固定 ja ko es fr de ru（518 行）
  extras.tsv    后加的新键，列序 zh-CN zh-TW en ar ja ko es fr de ru（13 行）
  ar_mp.tsv     阿语补译 45 条（mp_ 小程序独有 + ai_badge_hd）
        ↓  node tools/i18n_gen.js
miniprogram/utils/lang/*.js            10 份 × 531 键
android-app/app/src/main/res/values-*/strings.xml   10 份 × 451 条
```

**为什么不用「App 资源导出」这一招了**：前 4 语确实是 `res/values*/strings.xml` 导出，但新增的 6 语在 App 里原本不存在，只能先有译表再同时生成两端。现在反向也通了——改一条文案改译表、重跑一次，两端同步。

🔴 **生成器对已存在的 strings.xml 只追加、不重写**：原文件里有大量人工注释（占位符规则、RTL 提醒、条数约束）。第一版生成器整份覆盖，把 `values-ar` 的说明注释全冲掉了，已改回追加模式并从 git 恢复。

🔴 **译表里的 `\n` 是两个字面字符**，生成时还原为真换行，再由 JSON / Android 各自转义 —— 避免在三种转义体系之间来回猜。

### 2.1 校验（每次生成后都跑）

| 项 | 结果 |
|---|---|
| 10 份小程序包键数一致 | 531 / 531 / … / 531 |
| 10 份 App strings.xml 条数一致 | 451 / 451 / … / 451 |
| 占位符（`%1$s` `%2$d`）逐条比对 | 与中文基准 0 处不一致 |
| 原有 4 语内容回归 | 518 键**零改动**（新增仅 13 键） |
| 「与英文完全相同且中文不同」的条目 | 仅品牌名（WeChat / Alipay）、纯占位符、Pinyin / OK / Total 这类通用词 |

## 3 「不兼容 thumbcamera」的核实结论

不是「删掉双栈代码」，而是**本来就没有**：

```bash
grep -rn "thumbcamera" --include="*.kt" --include="*.gradle" --include="*.xml" \
     android-app/app/src android-app/app/build.gradle
# → 0 命中
```

| 位置 | 实际地址 |
|---|---|
| `RecordRepository.BASE_URL` | `https://nglearn.turingapi.com/` |
| `BuildConfig.RECORD_BASE_URL`（`build.gradle`） | 同上 |
| 小程序 `utils/api.js` `BASE` | `https://nglearn.turingapi.com` |

因此这次的工作不是拆除旧路径，而是**把客户端行为对齐到 nglearn 的最新接口形态**（§4）。真正需要「不再写 thumbcamera」的是文档——`docs/拍学机_设备端对接说明_V3.1-HW.md` 已标为内部留档，对外版本全部走 nglearn。

## 4 App 按最新接口文档改的 4 处

### 4.1 去掉失效的 `lang` 请求参数

**依据**：2026-10-28 只读实测——`/api/record/list?lang=en` 与不带 `lang` 返回完全一致。语言在**拍摄时**由云端按 `deviceId` 的设定固化。

| 端 | 改动 |
|---|---|
| App | `NameResolver.requestLangParam()` 恒返回 `null`（保留签名，避免调用点散落） |
| 小程序 | `api.listRecords` 删除 `lang` 字段；`today.js` / `cards.js` 不再传；`prefs.langParam()` 标注废弃 |

🔴 继续传 `lang` 不会报错，但会让人误以为「换语言能改历史记录」，而真实生效路径是设备侧设定语言。

### 4.2 `name_localized` 落缓存不再看请求参数

原代码：

```kotlin
if (langCode != null) persistLocalizedNames(fetched, langCode)   // ❌
```

一旦调用方不传 `lang`（本次正是如此），译名永远进不了缓存，界面表现为「选了日语一直显示中文 + 待翻译」。

现改为无条件调用，且**语言以 `name_localized_lang` 回显值为准**：

```kotlin
persistLocalizedNames(fetched, langCode)
// 内部：code = item.nameLocalizedLang ?: requestedLang
//       NameLanguage.fromCode(code).isChinese → 跳过（简体用原文、繁体本机转）
```

拿回显值还能挡住「服务端未支持该语言、把中文原样塞进 `name_localized`」——那种情况下 `fromCode` 得到的仍是中文，直接跳过，不会把中文当译名缓存。

### 4.3 新增 `tts_url_localized`（Room v3 → v4）

| 层 | 改动 |
|---|---|
| `RecordModels.RecordItem` | 加 `tts_url_localized` 字段 + `ttsLocalizedUrl` 取值器 |
| `WordCardEntity` | 加 `ttsLocalizedUrl: String?` |
| `AppDatabase` | `version = 4` + `MIGRATION_3_4`：`ALTER TABLE word_card ADD COLUMN ttsLocalizedUrl TEXT` + 注册 |
| `toEntity()` | 补映射 |

🔴 **必须显式写迁移**：`fallbackToDestructiveMigration` 会把 `bound_device` 一起清掉，用户升级后要重新配网。新列可空无默认值，老记录为 null，播放时按「localized → english → 中文」回落，不需要回填。

### 4.4 详情页优先播设定语言的音频

原逻辑：第一个发音按钮固定播 `tts_url`（中文）。选了日语也只能听中文，用户会判定「多语言没做」。

现在：

```kotlin
val playLocalized = !lang.isChinese && !lang.isNone && !localized.isNullOrBlank()
chineseUrl = if (playLocalized) localized else card.ttsChineseUrl
binding.btnPlayChinese.text =
    if (playLocalized) getString(R.string.detail_play_lang_fmt, lang.native)   // 「日本語 の発音」
    else getString(R.string.card_play_chinese)                                  // 「中文发音」
```

文案 `detail_play_lang_fmt` 进了 10 语。小程序详情页本来就有三路音频，本次把标签也改成「X 发音」而非只显示语言名。

---

### 4.5 语言写入云端：`POST /api/device/lang`（本轮补齐）

**这是本轮最关键的缺口。** 云端在 2026-10-28 02:25 上线了「按 `deviceId` 匹配语言、拍摄时固化进记录」的能力，但两端**一处都没调用**写入接口 —— 用户选的语言只存在手机本地，云端始终按默认 `zh` 产出名称。

现象：设置里显示「日本語」，拍出来还是中文，且不报任何错误。

```
v2.11.5 及之前：  选日语 → 写本地 SP → 拍照 → 云端查 deviceId 无记录 → 按 zh 返回
v2.11.6 起    ：  选日语 → 写本地 SP + POST /api/device/lang → 拍照 → 云端按 ja 返回
```

| 端 | 改动 |
|---|---|
| Android | 新增 `data/api/DeviceLangApi.kt`、`data/device/DeviceLangSync.kt`；`LanguageActivity.pick()` 上报、`BindRepository.bind()` 配网成功后补报、`MainActivity.onCreate()` 重试 pending |
| 小程序 | `utils/api.js` 加 POST 支持与 `setDeviceLang()`；新增 `utils/langSync.js`（多设备遍历 + pending）；`pages/language` 选择后上报、`pages/provision` 保存设备后上报 |

**接口契约已实测**（演示机 `c8586a630000`）：

| 调用 | 返回 |
|---|---|
| `GET /api/device/lang?key=&deviceId=` | `{"code":200,"data":{"device_id":"…","lang":"zh"}}` |
| `POST /api/device/lang?key=&deviceId=&lang=ja` | `{"code":200,"data":{"device_id":"…","lang":"ja"}}`，回读确认已变 ja |
| `POST` + JSON body 传参 | 🔴 **`4005 apikey信息错误`** —— 服务端不解析 POST body，参数必须走 query |
| `POST ...?lang=xx` | `40000 lang参数错误：支持 zh/zh-Hant/en/ja/ko/es/fr/de/ru/ar` |

**三条必须记住的边界：**

1. **白名单没有 `none`**。`none` 是客户端「仅英文」模式，上报时必须映射成 `en`。直接上报会拿 40000。
2. **云端语言按 `deviceId` 存，所以要多设备逐台上报**。只报当前设备会出现「这台改了、换一台又不行」；而语言页本身没有「当前设备」的概念（`CurrentDeviceStore.ALL` 是伪设备，不能上报）。
3. **pending 重试必须直接用云端语言码**，不能转回 `NameLanguage` 枚举 —— 枚举里**没有 `en`**（`none` 代表它），`fromCode("en")` 会静默回落成 `ZH`，结果是「仅英文模式下断网一次，重试把云端改成了中文」。

**失败处理**：没配网 / 断网 / 还没读到 apikey 都会失败，语言码记进 pending，在「进语言页 / 配网成功 / App 启动」三个时机补报；全部成功才清标记，不会每次进页面都白打请求。

## 5 已知差异与未做

| # | 项 | 说明 |
|---|---|---|
| 1 | App 的 `values-ja` 等 6 份是新翻译，**未做母语校对** | 结构、占位符、术语（卡片/相机/额度）已统一，上线前建议找母语者过一遍 |
| 2 | 德语 / 俄语长词 | 布局普遍是 `wrap_content`，但个别 12sp 副标题和 150dp 值列可能出现省略号，需要真机看一遍 |
| 3 | 系统语言自动跟随 | 首次启动仍默认简体，不读系统 locale（与 App 原行为一致） |
| 4 | 阿语 RTL | 未新增 RTL 相关改动；原有「布局全用 Start/End + 图标 `autoMirrored`」的约束继续有效 |
| 5 | 繁简转换 | 小程序仍是内置 ≈230 对字表（无 ICU），「干/面/台」这类多形字不转；App 用 Android ICU，正常 |
| 6 | **历史卡片不跟随语言** | 译名在拍摄那一刻由云端固化进 `name_localized`，切语言只影响**之后**拍的照片。这是既定产品口径，不是缺陷；UI 文案已按此表述 |
| 7 | 云端语言失败的补报只有三个时机 | 进语言页 / 配网成功 / App 启动。没有做后台定时重试（省电与请求量考虑）；语言不是时效性功能，晚几分钟生效可接受 |
